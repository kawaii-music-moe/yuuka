- ステータス: **段階 1〜4 を実装済み**（§11）。段階 5（管理画面の一覧・削除）は未着手。
- 対象: `crates/yuuka-orchestrator/src/synapse_extract.rs`（抽出）・`synapse_recall.rs`（想起）・`synapse_repo.rs`、`crates/yuuka-synapse`（索引）、`synapses` テーブル（`crates/yuuka-db/migrations/V17__baseline.sql`）。
- 上位の設計: [synapse_cognitive_architecture.md](synapse_cognitive_architecture.md)（§5.1 で「減衰/強化」を予定していたが、減衰と忘却は未実装）。

## 1. 今の仕組み（事実）

| 段階 | 今の実装 | 問題 |
|---|---|---|
| 抽出（書く） | ターン確定後、**利用者の発話そのもの**を、(a) 意味マーカー（好き・毎日・誕生日・覚え 等 27 語）を含む、または (b) **80 文字以上**なら、先頭 300 文字に切って保存。LLM は使わない | (b) で長文がほぼ全部残る。発話を要約も書き直しもしないので「事実」ではなく「発話の生テキスト」が溜まる |
| 入力の中身 | Discord の返信は `[返信先メッセージ (あなた): "…"]` が先頭に付いた文字列で渡る（`message_flow.rs`） | **Bot 自身の返答**が利用者の記憶として保存される |
| 想起（読む） | 文字 n-gram のハッシュ埋め込みでコサイン上位 5 件＋時刻・最近性の補正。想起したら `use_count` と `decay_score` を +1 | 想起＝有用ではない。`decay_score` は増えるだけで順位にも使われず、減衰しない |
| 忘却 | なし。スコープあたり 5000 件で最古を追い出すだけ | 消えない。利用者からも見えず消せない |
| 評価 | なし（`recall_hit` / `recall_empty` の件数だけ） | 良い記憶が残っているかを測る手段がない |

## 2. 本番データで見えたこと（2026-11-11・`data/yuuka.db`）

| 指標 | 値 |
|---|---|
| 件数 | 503（7 月から。10〜11 月は利用者発話 1,211 件中 127 件を保存） |
| `[返信先メッセージ` で始まる（＝Bot の返答が混入） | **278 件（55%）** |
| 300 文字の上限に当たった（長文の切り捨て） | 280 件（56%） |
| ギルド（汎用モード）由来 | 501 件（秘書由来は 2 件） |
| 同一内容の重複 | 17 組 |
| 想起回数の偏り | 上位 10 件はすべて返信プレフィックス付きか歌詞のコピペで、各 190〜385 回想起 |
| 直近の保存内容 | 数学の計算ミスへの罵倒の長文が 20 件以上連続（長さだけで保存） |

つまり「全部保存して重み付け」の状態で、**重み（`use_count`）は内容の価値ではなく、字面が似た定型（返信プレフィックス）の多さ**を測っている。想起 5 件のうち大半がこれらで埋まり、本当に役立つ記憶が出てこない。

## 3. 目標

「記憶に値するか」を 3 つの軸で評価し、残すのは評価を通ったものだけにする。

| 軸 | 問い | 例 |
|---|---|---|
| 持続性 | 来月も真である事実か | 「乳製品アレルギー」「金曜は在宅」は残す。「今日は疲れた」「この式の符号が違う」は残さない |
| 本人性 | 利用者自身についての情報か | 「○○が好き」「卒論のテーマはノイズミュージック」は残す。歌詞のコピペ・Bot の返答は残さない |
| 再利用性 | 実際に返答に効いたか | 想起されて返答に使われた記憶は強め、何度想起されても使われない記憶は弱める |

到達点: 利用者 1 人あたり数十〜数百件の「短い事実文」だけが残り、想起 5 件が毎回それなりに関係する。利用者は自分の記憶を一覧・削除できる。

## 4. 設計: 3 段のパイプライン

```
発話 ─▶ [A 入口フィルタ]（同期・LLM なし）─▶ 候補 ─▶ [B 評価器]（非同期・バッチ・LLM）─▶ 記憶
                                                                                    │
                                              [C 保持と忘却]（毎日の cron）◀─────────┘
                                                   ▲
                                   [D 有用性の信号]（返答後に軽い判定）
```

### A. 入口フィルタ（Rust・ターン内・ゼロコスト）

目的: 明らかなゴミを候補にしない。

1. 返信プレフィックス `[返信先メッセージ (…): "…"]` を**抽出の前に剥がす**（エンジンに渡す前に `IncomingChat` に「返信元」と「本文」を分けて持たせ、抽出は本文だけを見る）。
2. 本文の大半が引用・コードブロック・URL・数式・歌詞らしい繰り返し（同じ行の反復）なら候補にしない。
3. 「長さだけ」の基準（80 文字以上）を廃止する。候補にするのは、意味マーカーを含むか、一人称の断定文（「私は」「俺は」「僕は」「うち」＋「だ/です/てる/ている」）を含むものに限る。
4. 正規化した内容のハッシュで同一内容を弾き、同スコープで既存記憶とコサイン 0.95 以上なら候補にしない（近い重複）。
5. 利用者×Bot あたり 1 日の候補数に上限（例 20）。超えた分は捨てる。
6. 秘匿ガードは今のまま。

### B. 評価器（LLM・非同期・バッチ）

目的: 候補を「短い事実文」に書き直し、残す価値を判定する。

- 候補は `synapses` に `status='candidate'` で入れ、埋め込みは付けず想起にも出さない。
- 評価は **1 日 1 回**（または候補が 10 件溜まったら）、利用者×Bot ごとにまとめて 1 回の LLM 呼び出しで行う。利用者本人の Gemini キー（既存の `AuxTextGenerator` ポート。秘書は本人キー、汎用モードは Bot 専用キー）。
- 出力は候補ごとに `{ keep, kind, statement, durability, confidence }`。
  - `kind`: preference / fact / constraint / relationship / event / instruction
  - `statement`: 三人称の短い事実文（80 文字以内。「利用者は乳製品アレルギーがある」）。
  - `durability`: long（1 年）/ medium（3 か月）/ short（2 週間）。`keep=false` は削除。
- `keep=true` のものだけ `status='kept'` にし、`content` を `statement` に置き換え、埋め込みを作って索引へ入れる。元の発話は `source_msg_id` で辿れるので保存しない。
- キーが無い・呼び出しに失敗した利用者は、A を通った候補のうち**意味マーカーを含むものだけ**を kept にする（今より厳しい heuristic へ縮退）。候補のまま 7 日たったものは捨てる。
- プロンプトの入力は候補 30 件・約 2,000 トークン。Free Tier でも 1 日 1 回なら収まる。

### C. 保持と忘却（Rust cron・毎日）

目的: 残したものも、使われなければ消える。

- `strength`（今の `decay_score` の意味を変える）を本当の強度にする: 毎日 `strength *= 0.97`（半減期 約 23 日）。D の「有用」で `+1.0`、想起だけでは `+0.1`。`durability=long` は減衰を半分にする。
- 削除: `strength < 0.2` かつ最終有用から `durability` の期間を過ぎたものを消す（索引からも `forget`）。
- 上限: 利用者×Bot あたり kept の上限（秘書 500・ギルド 300。設定で変更可）。超えたら `strength` が低い順に消す。
- 併合: 同スコープでコサイン 0.92 以上の 2 件は新しい方を残し、`strength` を足す。
- 消した件数・残った件数を `[Metrics]` に出す。

### D. 有用性の信号（軽い判定）

目的: 「想起された」と「役に立った」を分ける。

- 返答確定後、想起した 5 件それぞれについて、記憶の `statement` の内容語（名詞・固有名詞っぽい 2 文字以上のトークン）が返答本文に 1 つ以上含まれていれば「有用」とみなし `useful_count += 1`・`strength += 1.0`。含まれなければ `+0.1` のみ。
- 精度は粗くてよい（B の評価が主、D は強弱の補正）。将来、B の評価器に「直近の想起が役に立ったか」を月 1 回サンプル判定させる案もある。

### E. 利用者から見える

- 管理画面「あなたの設定」に「記憶」を足す: 一覧（statement・kind・最終利用・strength）、削除、「これは覚えないで」のトグル。LLM ツールにも `forgetMemory` を足す。
- プライバシー: 記憶はこれまでどおり利用者×Bot でしか読めない。汎用モードのギルド記憶は発話者本人の分しか想起しない（今と同じ）。

## 5. スキーマ変更（V37）

`synapses` に列を足す（既存行は `status='kept'`・`kind=NULL`・`durability='medium'`・`strength=decay_score` で埋める）。

| 列 | 型 | 用途 |
|---|---|---|
| `status` | TEXT NOT NULL DEFAULT 'kept' | candidate / kept |
| `kind` | TEXT | B の分類 |
| `durability` | TEXT NOT NULL DEFAULT 'medium' | long / medium / short |
| `strength` | REAL NOT NULL DEFAULT 1.0 | C の強度（`decay_score` は読まなくなる。列は残す） |
| `useful_count` | INTEGER NOT NULL DEFAULT 0 | D |
| `last_useful_at` | TEXT | D |
| `evaluated_at` | TEXT | B |
| `content_hash` | TEXT | A の重複排除 |

`synapses(user_id, bot_id, status)` と `(user_id, bot_id, content_hash)` に索引。RAM 索引は `status='kept'` だけ読む。

## 7. 効果の測り方

| 指標 | 今 | 目標 | 測り方 |
|---|---|---|---|
| Bot 返答の混入率 | 55% | 0% | `content LIKE '[返信先%'` |
| 1 件の長さ | 平均 208 文字 | 80 文字以内 | `avg(length(content))` |
| 想起の的中率 | 未計測 | 5 件中 2 件以上が関係する | 週 1 回、想起 20 件を人手で○×（管理画面に「この記憶は関係ない」ボタンを付ければ利用者の○×で代替できる） |
| 30 日以内に有用だった記憶の割合 | 未計測 | 30% 以上 | `useful_count` と `last_useful_at` |
| 利用者あたり件数 | 最大 147 | 上限以内で安定 | `[Metrics]` の `synapse_kept` / `synapse_forgotten` |

A を入れる前に、今の DB で上の「今」の値を取ってベースラインにする（§2 の数字がそれ）。

## 8. 決めてもらうこと

1. **評価に LLM を使ってよいか。** 利用者本人のキーで 1 日 1 回。費用は本人負担（Free Tier なら無料枠内）。使わない場合は A と C だけで進め、B は意味マーカーだけの縮退版になる。
2. **汎用モード（ギルド）の記憶を続けるか。** 今の 503 件のうち 501 件がギルド由来で、内容の多くは秘書的な「本人の事実」ではない。ギルドでは記憶を切る（または上限を小さくする）のが簡単で効果が大きい。
3. **既存の 503 件を評価し直してよいか**（§6）。全部消して新規に始める選択もある。
4. 上限（秘書 500・ギルド 300）と半減期（約 23 日）の初期値。あとから設定で変えられるようにする。
