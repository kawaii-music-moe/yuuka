01

全体構成

本番イメージでは Rust バイナリ yuuka が HTTP/API と会話エンジンを起動し、ビルド済み Svelte SPA を同じ HTTP サーバーから配信します。SQLite が業務データの正本、Redis はセッション用です。

実行ゲート: Discord gateway は YUUKA_RUST_DISCORD で制御され、既定では無効です。Docker イメージでは YUUKA_RUST_CRON=1 が設定され、Rust が cron を所有します。運用時の有効状態は環境設定を確認してください。
02

実行単位と境界

本番アプリコンテナ

Compose の app は yuuka:latest を実行。ポート 7854 に bind し、config と data volume を mount。SPA は dist/public から配信します。

Redis コンテナ

セッション用途。Compose 設定では Redis 永続化を無効化し、コンテナ再作成時のデータ再構築は不要なキャッシュとして扱います。

ビルド時フロントエンド

ルート package.json の build は Rust release バイナリと Vite SPA を構築。成果物は Rust サーバーと同じデプロイ単位へ入ります。

別配布・補助クライアント

Windows 向け egui Desktop のソースと Vue ベースの PWA クライアントがリポジトリ内にあります。主なデプロイ経路の Svelte 管理 SPA とは別の成果物です。

04

主要データフロー

チャット・Function Calling

ユーザー入力が Discord gateway または /ws/chat から入る。WebSocket では session / bearer identity と bot access を確認。

ChatEngine がユーザー・Bot・guild 文脈、persona / module 設定、会話履歴を構成。

Gemini へ prompt と利用可能な tools を送り、tool call が返れば registry が handler を dispatch。

ドメイン repo が SQLite を読書きし、結果を会話 loop に返す。必要なとき追加の Gemini turn を行い、最終返信を元チャネルへ返す。

Web 管理 API

Svelte SPA は same-origin /api/* を呼び、認証状態を /api/me で初期化。

Axum route が認証・CSRF・role・bot ownership を検証して機能 crate の handler へ。

repo はユーザー / Bot スコープを受け取り SQLite writer actor または read pool を利用。

JSON DTO を返し、画面 store / route が状態を更新。開発時 Vite は /api と /ws/chat を API へ proxy。

Synapse 記憶フロー

起動時に yuuka-synapse が DB から記憶と embedding を読み RAM index を構築。ChatEngine の想起 / 抽出が同じ engine を共有します。起動時読込に失敗しても空 index で起動を継続し、想起を空結果へ縮退させます。

05

データ・分離モデル

SQLite が正本

既存 DB ファイルを開き、Refinery の前方マイグレーションを writer 起動時に適用します。WAL、foreign keys、有効な read-only pool、および単一 writer actor を使い、アプリ内の書込み経路を集約します。

マルチテナント境界

個人データは Discord user ID を基礎スコープとし、Bot / guild 固有データには bot_id / guild_id を加えます。アクセス判定は route / service / repo の該当操作で行います。

Redis はセッション専用

Cookie セッションの共有ストア。Bearer desktop token は SQLite 側。Redis に接続できない場合は起動を継続する縮退経路があり、利用できない機能の振る舞いは auth backend に依存します。

スキーマの所有

現 Rust 実装では crates/yuuka-db/migrations が migration 所有者です。適用される系列は baseline V17 と V18〜V22 の前方マイグレーションです。

代表的な永続機能: users / sessions & desktop tokens / bots & memberships / message logs / todos / expenses / schedules / reminders / contacts / credentials / personas / playbooks / settings / synapses。完全な制約・列・索引は migration SQL と architecture 規範を参照してください。

07

起動・運用

設定 config.yaml と環境変数を読み、暗号鍵の存在・強度などを検証。不備は fail-fast。

既存 SQLite を開き migrations を適用。YUUKA_ENCRYPTION_SECRET_NEW 指定時はサービス開始前に旧鍵から再暗号化。

Redis session store 接続。到達不能でも縮退起動し、Auth・crypto・共有 reqwest / MCP / Google / Synapse / ChatEngine を構築。

HTTP service を Supervisor へ登録し bind / serve。障害時は supervised task として再起動対象。設定不備等の起動エラーは非ゼロ終了。

Discord gateway と cron は環境変数で個別に制御。shutdown 時は監督下 service を停止し graceful shutdown。

Compose トポロジ

docker-compose.yml は app + Redis の構成。app は設定ファイルを read-only mount、SQLite その他のデータを /app/data に mount。ホスト bind address / port と PUID/PGID を instance env から受け取ります。

08

セキュリティ設計上の要点

認証と権限

  • Web cookie session と desktop bearer token の認証経路。
  • admin role、Bot 所有・共有・guild membership などのアクセス制御。
  • パスワードの bcrypt とレート制限を auth crate に集約。

保存時暗号化

  • AES-256-GCM による機密列の保存時暗号化。
  • system secret を起動時に検査、必要なら鍵ローテーション。
  • Gemini / Discord / Google credentials 等に暗号実装を共有。

DB 書込み制御

  • Read connection は read-only + query_only。
  • 全書込を単一 writer actor に通し、transaction を明示。
  • DB busy は層別エラーへ写像し retry 可能に扱う。

LLM tool の権限面

  • 利用可能機能は Bot capability と有効 module で選別。
  • ユーザー×Bot 上書き設定を扱う。
  • 外部 MCP 呼出は接続先 / proxy の検査を挟む。
