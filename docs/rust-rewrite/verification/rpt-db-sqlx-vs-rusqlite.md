# Rust SQLite Database Crates — Research Findings (July 2026)

All version numbers and release dates below were verified against the crates.io API and official docs.rs / GitHub sources. URLs cited at the end.

---

## 1. sqlx

**Latest version: `0.9.0`, released 2026-05-21** (confidence: 高). The SQLite sub-crate `sqlx-sqlite` is also `0.9.0` (same date). Note: 0.9.0 is fairly recent — the prior stable line was 0.8.x (0.8.6 was 2025-05-19), so 0.9.0 represents a ~1-year major-ish jump with breaking changes. Note also the repo has moved to the `transact-rs/sqlx` org (redirected from `launchbadge/sqlx`).

**SQLite support: Yes** (confidence: 高). sqlx supports PostgreSQL, MySQL/MariaDB, and SQLite. As of 0.9.0 the `sqlite` feature bundles the SQLite C source and static-links it (it pulls in `sqlite-bundled`, `sqlite-deserialize`, `sqlite-load-extension`, `sqlite-unlock-notify`); `sqlite-unbundled` links a system SQLite instead. Only one `libsqlite3-sys` version may appear in the dependency tree.

**Compile-time query checking (`query!` / `query_as!`) with SQLite: Yes, but with real caveats vs Postgres** (confidence: 高).
- The macros require `DATABASE_URL` at build time pointing at a real database of the same kind and schema (data not required). Offline mode via the `.sqlx` directory (generated by `sqlx-cli prepare`) is now always enabled, removing the need for a live DB in CI.
- Nullability inference for SQLite works by checking `NOT NULL` constraints on source columns and stepping through `EXPLAIN` output. It is more fragile than Postgres: a `NOT NULL` column brought in via a `LEFT JOIN` can actually be `NULL`, producing a runtime `UnexpectedNull` error if inference is wrong. Postgres additionally uses `EXPLAIN VERBOSE` analysis to catch outer-join nullability; SQLite's `EXPLAIN`-based approach has more gaps (e.g. GitHub issue #3286 documents failure to infer subquery nullability/type).
- SQLite's dynamic typing means fewer schema type hints, so custom/date-time types often need explicit overrides: `col as "col: T"`, force-not-null `col as "col!"`, force-nullable `col as "col?"`. Community reports (Discussion #3684) note this gets verbose for wide result sets.

**Internal SQLite architecture — dedicated blocking thread per connection** (confidence: 高, verified from source `sqlx-sqlite/src/connection/worker.rs`).
- sqlx is async but SQLite's C API is synchronous/blocking. sqlx wraps it by spawning **one dedicated OS thread per SQLite connection** (via `thread::Builder::new().spawn(...)`; source comment: "Each SQLite connection has a dedicated thread"). A source TODO notes intent to eventually use a thread pool per connection-pool to reduce OS resource usage — so as of 0.9.0 it is still strictly one thread per connection.
- The async side (`ConnectionWorker`) sends a `Command` enum (`Prepare`, `Execute`, `Begin`, `Commit`, `Rollback`, …) over a bounded `flume` channel to the worker thread; each command carries a `oneshot`/`flume` response channel. Transactions use a `rendezvous_oneshot` mechanism to guarantee acknowledgment ordering. `WorkerSharedState` holds transaction depth and a `Mutex<ConnectionState>`.
- `SqlitePool` is the standard `sqlx::Pool<Sqlite>`; each pooled connection = one such worker thread.

**WAL / pragmas via `SqliteConnectOptions`** (confidence: 高, verified defaults from docs.rs):
- Builder methods: `journal_mode(SqliteJournalMode)`, `busy_timeout(Duration)`, `foreign_keys(bool)`, `synchronous(SqliteSynchronous)`, `pragma(key, value)` (arbitrary), `create_if_missing(bool)`, `shared_cache(bool)`, `serialized(bool)`.
- WAL is set with `.journal_mode(SqliteJournalMode::Wal)`.
- **Defaults**: sqlx does **not** set a journal mode by default (deliberately, to avoid flipping a DB into/out of WAL); non-WAL default is `DELETE` (`MEMORY` for in-memory). **busy_timeout defaults to 5 seconds.** `foreign_keys` is **ON by default** (a deliberate sqlx choice). `synchronous` defaults to `FULL` (docs suggest `NORMAL` is sufficient in WAL if durability-on-crash isn't critical). Statement cache defaults to 100.

**Runtime / TLS feature flags in 0.9.0** (confidence: 高): 43 feature flags; the 5 defaults are `any`, `json`, `macros`, `migrate`, `derive` — **no runtime, no TLS, and no DB driver are enabled by default** (you must opt in).
- Runtime: `runtime-tokio`, `runtime-smol`, `runtime-async-global-executor`. The old combined `runtime-tokio-native-tls`-style features were **deleted** in 0.9.0. `async-std` support was dropped in favor of `runtime-smol` / `runtime-async-global-executor`.
- TLS: `tls-native-tls`, `tls-rustls`, `tls-rustls-ring`, `tls-rustls-aws-lc-rs` (rustls 0.23 with pluggable crypto providers; `tls-rustls` = ring for back-comat).
- 0.9.0 SQLite breaking changes: extension loading is now `unsafe`; `SqliteValue`/`SqliteValueRef` made `!Send`/`!Sync`; `libsqlite3-sys` now range-versioned. TLS is largely irrelevant for SQLite (local file), so for a SQLite-only build you typically only need `runtime-tokio` + `sqlite` + `macros`.

## 2. rusqlite

**Latest version: `0.40.1`, released 2026-06-06** (confidence: 高). Recent cadence: 0.40.0 (2026-05-26), 0.39.0 (2026-03-15), 0.38.0 (2025-12-20), 0.37.0 (2025-07-06) — **actively and frequently maintained**. (The initial search summary claiming "0.38.0 is latest" was stale; the crates.io API confirms 0.40.1.)

**Synchronous/blocking — confirmed** (confidence: 高). rusqlite is a thin ergonomic wrapper over the SQLite C API with no async layer. Under tokio you must not call it directly on an async task; the standard pattern is `tokio::task::spawn_blocking(move || { conn.execute(...) })` (or a dedicated blocking thread) so it runs on the blocking thread pool. For pooling:
- **`r2d2` + `r2d2_sqlite`** (synchronous pool): `r2d2_sqlite` latest **`0.34.0`, 2026-05-10** — actively maintained. Combine with `spawn_blocking`.
- **`deadpool-sqlite`** (async pool built for rusqlite): latest **`0.13.0`, 2026-02-17** — actively maintained (author bikeshedder). It wraps each rusqlite connection and runs operations on a separate thread internally, giving an async-friendly `interact()`-style API, so you don't hand-roll `spawn_blocking`.
- **`deadpool-rusqlite` does not exist** (confidence: 高 — the crate name 404s; the correct crate is `deadpool-sqlite`). So the pool choices are: `r2d2_sqlite` (sync) vs `deadpool-sqlite` (async). Both are current in 2026.

**`bundled` feature / bundled SQLite version** (confidence: 高, verified from rusqlite master README): rusqlite 0.40.1 depends on `libsqlite3-sys ^0.38.1`. With the `bundled` feature, the README states verbatim: *"This source is embedded in the `libsqlite3-sys` crate and is currently SQLite 3.53.2 (as of `rusqlite` 0.40.1 / `libsqlite3-sys` 0.38.1)."* `bundled` compiles and statically links a known-good SQLite, avoiding reliance on the system SQLite version.

**WAL + busy_timeout in rusqlite** (confidence: 高): configured by executing pragmas on the connection: `conn.pragma_update(None, "journal_mode", "WAL")` (or `conn.execute_batch("PRAGMA journal_mode=WAL;")`), and `conn.busy_timeout(Duration)` (or `PRAGMA busy_timeout=...`). Unlike sqlx, rusqlite sets **no defaults** — you must set journal_mode, busy_timeout, foreign_keys, synchronous yourself. There is no built-in typed options builder like `SqliteConnectOptions`; you issue raw pragmas after opening.

## 3. General consensus & trade-offs (2026): sqlx-sqlite vs rusqlite+spawn_blocking+pool

Confidence: 中〜高. This is well-documented in the community (notably the widely-cited Evan Schwartz "PSA: Your SQLite Connection Pool Might Be Ruining Your Write Performance" analysis), plus long-standing sqlx issues (#326, #451 "database is locked").

**The core SQLite reality:** even in WAL mode SQLite allows **many concurrent readers but exactly one writer**. Any design that lets multiple connections attempt writes concurrently will serialize at the SQLite write lock — and if a task holds the write transaction across an `await` and the async runtime schedules another writer, that writer spins until `busy_timeout` and then returns `SQLITE_BUSY`.

**Known sqlx-specific pitfall (the biggest gotcha):** A default `SqlitePool` with N connections (e.g. 5–50) is an anti-pattern for write-heavy WAL workloads. Because sqlx yields at `await` points while a connection may hold the write lock, multiple pooled writers contend and hit `busy_timeout`, causing lock starvation. Benchmarks in the referenced PSA show a naive 50-connection pool at ~2,586 rows/sec vs a single-writer connection at ~60,061 rows/sec — roughly **20x**. The community fix is to mirror SQLite's model at the app layer: **two pools** — a read pool (many connections, WAL readers scale fine) and a write pool with **`max_connections(1)`** so writes queue instead of contending. This is not a sqlx bug per se but an architectural mismatch users repeatedly hit. sqlx's own `SqliteConnectOptions` docs do not yet prescribe this pattern, so it's easy to miss.

**Trade-off summary:**

| | sqlx-sqlite (0.9.0) | rusqlite (0.40.1) + spawn_blocking/pool |
|---|---|---|
| Async | Native async; one dedicated OS thread per connection under the hood | Synchronous; you bridge via `spawn_blocking` or `deadpool-sqlite` |
| Compile-time checked queries | Yes (`query!`/`query_as!`), with SQLite nullability/type-inference caveats & verbose overrides | No (runtime-checked SQL) |
| Multi-DB portability | Same API across PG/MySQL/SQLite | SQLite-only, but full/idiomatic SQLite access |
| Control over pragmas/threading | Typed `SqliteConnectOptions`, sane defaults (busy_timeout 5s, FK on) | Raw pragmas, full control, no defaults |
| Write-concurrency footgun | Real risk with default multi-conn pool; needs manual 1-writer-pool split | You naturally structure a single writer thread; explicit and predictable |
| SQLite feature depth | Good, but abstracted (extensions now `unsafe`, deserialize behind feature) | Deepest access: hooks, custom functions, VFS, blob I/O, backup API, etc. |
| Bundled SQLite | Bundles SQLite 3 (static) via `sqlite` feature | Bundles SQLite **3.53.2** via `bundled` |

**Practical recommendation for a high-reliability WAL service with concurrent read+write:**
- If you want ergonomics, migrations, compile-time-checked queries, and multi-DB flexibility: **sqlx-sqlite is fine and current — but you MUST adopt the split-pool pattern** (separate read pool + single-connection write pool), set `journal_mode=WAL`, an explicit `busy_timeout` (5s default is a floor), and `synchronous=NORMAL` under WAL. Without the single-writer discipline you will hit `SQLITE_BUSY`/lock-starvation under write load — the single most reported sqlx-SQLite issue.
- If you want maximum control, predictable write serialization, deepest SQLite feature access, and are comfortable managing the async bridge: **rusqlite + a dedicated single writer thread (spawn_blocking or a `max_size=1` write pool) + a read pool** (`r2d2_sqlite` or `deadpool-sqlite`). This maps most directly onto SQLite's one-writer/many-reader model and is the common choice for write-heavy, high-reliability services. rusqlite also lets you pin an exact bundled SQLite (3.53.2) for reproducibility.

Both crates are healthy and actively maintained in 2026; the decision hinges on async-native ergonomics + compile-time query checking (sqlx) vs. control + write-path predictability + SQLite feature depth (rusqlite). In either case, the WAL single-writer discipline is the load-bearing design decision, not the crate choice.
