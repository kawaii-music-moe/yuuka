yuuka 音声チャットの構成

PWA の「音声」画面（/voice）で、Web 版チャットを声だけで使う仕組みです。読み上げには Irodori-TTS v4.1-Small-MF を使い、普段は端末の GPU で、GPU の無い端末ではサーバーで声を作ります。develop e4e8567（PR #223・#225）時点の内容です。

全体図

端末・yuuka 本体・同じホストの 3 か所に分かれます。音声の入力と再生は常に端末で行い、声を作る場所だけが変わります。

青い枠が音声生成の本筋です。端末で作るときは左の縦の列、サーバーで作るときは ServerSpeaker → tts_proxy.rs → yuuka-tts.service と進みます。

1 回のやりとり

  1. 聞くlistenOnce()（Web Speech API）で文字にする。途中経過も画面に出す
  2. 送る既存のチャット API（agentGateway）にそのまま送る。音声専用のチャットはない
  3. 文に分けるspeechSentences() が Markdown を読める文に直し、80 字までに区切る。最初の文は 24 字前後で読点で切り、最初の音を早くする
  4. 声を作る文ごとに生成し、区切り（チャンク）ごとに音声を返す
  5. 鳴らすChunkPlayer（Web Audio）が届いた順に続けて鳴らす。止める・割り込むと残りを捨てる
  6. また聞くハンズフリーがオンなら、読み終えたら 1 に戻る

生成の場所の選び方

VoicePage.vue の checkEngine() が、開いたときに 1 回だけ決めます。状態は checking / needs-download / loading / ready / server / browser / none です。

条件使うもの状態
設定「サーバーで声を作る」がオンで、サーバーでの生成が使えるServerSpeakerserver
WebGPU が使え、モデルが端末に保存済みIrodoriSpeaker（そのまま読み込む）loading → ready
WebGPU が使え、モデルが未保存「音声モデルを準備する」ボタンを出す（約 1.7 GB）needs-download
WebGPU が使えない・読み込みに失敗したサーバーでの生成が使えれば ServerSpeaker、無ければ標準の読み上げserver / browser / none

「サーバーでの生成が使える」は GET /api/client/tts/status が 200 を返すかどうかで判定します（本体に TTS_SERVER_URL が無ければ 404、音声生成サーバーが落ちていれば 503）。

音声生成の中身（pipeline.ts）

ブラウザ（worker.ts）とサーバー（engine.ts）は同じ IrodoriTts クラスを使います。違うのは onnxruntime が web（WebGPU）か node（CPU）かだけです。1 文ずつ次の順に処理します。

  1. 文字の整形と分割text.ts の自前 Unigram トークナイザ（Python 版と 415/415 一致）
  2. cond_encoder本文とキャプション（声の説明）を ModernBERT-ja でベクトルに
  3. duration音声の長さ（フレーム数）を予測する。話者条件は「参照なし」で渡す
  4. dit_step × 4MeanFlow 4 ステップで音の潜在（25 フレーム/秒）を作る
  5. 末尾を切るfindFlatteningPoint() で末尾の無音を落とす
  6. dacvae_decoder区切りごとに 48 kHz の波形へ。最初 20 フレーム、以降は倍々。前後 8 フレームの文脈を付け、一括デコードと同じ音になる

生成は async generator（synthesize()）で、区切りごとに音声を返します。止めるときは isCancelled を見て途中でやめます。

声（話者条件）

文ごとに乱数を変えるだけだと声色が変わってしまうので、声は「話者条件」（tokens × 768 の f32 行列と mask）に固めて、全部の文で同じものを使います。作り方は 2 つです。

説明から作る design

  1. キャプション（「落ち着いた若い女性の声」など）と声の番号（seed）を決める
  2. 見本の文を 1 回だけ生成する
  3. その潜在を speaker_encoder に通して話者条件にする

保存前は VoiceSpec {kind:'design', caption, voiceSeed} のまま渡し、Worker やサーバーが作って覚えておく。

サンプル音声から作る clone

  1. ファイル（MP3 など）か録音（最長 30 秒）を voiceSample.ts で 48 kHz モノラルに
  2. prepareReference() で最長 120 秒・-16 LUFS（BS.1770）にそろえる
  3. dacvae_encoder → speaker_encoder で話者条件に

サーバーで作るときは 16 bit PCM で先頭 60 秒まで送る。dacvae_encoder は声を作るときだけ要るので、端末では後から読み込む。

サーバーでの生成（GPU の無い端末向け）

音声生成サーバー（clients/pwa/server/tts/server.ts）は認証を持たず 127.0.0.1 で待ち受けます。端末からは必ず本体の /api/client/tts/{op} を通り、本体がログイン済みかを確かめてから転送します（応答はストリームのまま）。

操作送るもの返るもの
GET status—{ ok, loaded, model }
POST speak{ text, voice, seed, durationScale }16 bit PCM（48 kHz モノラル）を区切りごとに流す
POST design{ caption, voiceSeed }話者条件 { stateBase64, mask }
POST clone{ pcmBase64 }（3 秒以上）話者条件
  • 保存した声の渡し方：サーバーは話者条件を key（声の id と作成日時）で 16 件まで覚えます。端末はそのページで初めて使う声だけ話者条件を付けて送り、以降は key だけ送ります。サーバーが再起動して忘れていれば 428 が返るので、付けて送り直します。
  • 処理の順番：CPU を 1 件で使い切るので、要求は 1 件ずつ順に処理します。
  • メモリ：最初の要求でモデルを読み込み（約 8 秒）、生成中は約 3.7 GB（ピーク約 4.9 GB）です。10 分使われなければ解放します。CPU のメモリアリーナは切っています（入れると約 6.4 GB）。
  • 速さ（スレッド 3）：最初の音まで約 1.9 秒、生成にかかる時間は音声の長さの約 1.1 倍です。int8 量子化は音質と長さが変わるので使っていません。

声の保存

作った声は作った本人だけが、どの端末からでも使えるようにサーバーに保存します。サンプル音声そのものは保存せず、話者条件だけを保存します。

API（voices.rs）内容
GET /api/client/voices自分の声の一覧（mask は含むが、話者条件の行列は含まない）
POST /api/client/voices保存。1 人 30 件まで・tokens 1024 まで・名前 40 字・キャプション 200 字
PATCH /api/client/voices/{id}名前・キャプションの変更
DELETE /api/client/voices/{id}削除
GET /api/client/voices/{id}/state話者条件（f32 のバイト列）
  • DB：client_voices（V36）。speaker_state は BLOB、speaker_mask は JSON、speaker_model は作ったモデルの系統（今は irodori-v4.1-small-mf）。違う系統の声は一覧で「今の音声モデルでは使えません」と表示します。
  • 端末のキャッシュ：voiceStore.ts が話者条件を OPFS に {id}-{作成日時}.f32 で置き、2 回目からはダウンロードしません。
  • 古い保存先：以前の端末内だけの保存は、一覧を開いたときにサーバーへ移します。

モデル

モデルはリポジトリに含めず、tools/irodori-onnx/ で作って各環境の data/tts-models/<版>/ に置きます。今の版は irodori-v41-mf-fp16-3 です。版ごとのフォルダは書き換えず（immutable で配信）、変えるときは新しい版を作って MODEL_VERSION を上げます。

ファイル精度大きさ役割
cond_encoderfp16640 MB本文・キャプションのエンコーダ
durationfp3287 MB長さの予測
dit_stepfp16749 MBMeanFlow の 1 ステップ（4 回呼ぶ）
dacvae_decoderfp16167 MB潜在 → 48 kHz 波形（noguchis/irodori-tts-onnx の codec）
speaker_encoderfp16123 MB潜在 → 話者条件
dacvae_encoder optionalfp1656 MBサンプル音声 → 潜在（声を作るときだけ）
tokenizer.json ほか—4 MBトークナイザ・設定・参照なしの話者条件・manifest.json
  • 端末での保存：OPFS に置きます（Cache Storage は 700 MB 前後のファイルで失敗するため）。manifest.json だけ no-cache で、版が変わると古いフォルダを消します。Service Worker（sw.js）は /tts-models/ を扱いません。
  • WebGPU の設定：onnxruntime-web 1.23.2 を Web Worker で動かし、numThreads=1 です（CSP で blob: URL を使えないため）。asyncify 版の wasm は vite の ?url で自分のサーバーから配ります。
  • 変換：export.py が torch.onnx（dynamo）で書き出し、export_patches.py が書き出せない箇所（RoPE の複素数・データで分岐するマスク・長さの固定）を直します。golden.py で PyTorch との一致を確かめ、package.py で版のフォルダにまとめます。作業環境は ~/apps/irodori-tts です。

落とし穴

  • 長さの予測は参照なしで：参照ありの話者条件で長さを予測すると、文の長さに関係なく約 3.4 秒になります（上流の PyTorch 版も同じ）。
  • キャプションには rare-token split をかけない：本文だけにかけます。かけると長さがずれます。
  • fp16 の Clip：WebGPU でシェーダーエラーになるので、話者エンコーダの平均トークンは fp32 で計算しています。
  • WASM の実行環境では動かない：fp16 モデルはメモリ不足になるので、端末では WebGPU だけを使います。
  • Iris Xe などでたまに数値エラー（例：37602664）：読み込み直すと直ることが多いので、再読み込みボタンを出し、失敗したらセッションを解放します。
  • モデルを差し替えるとき：MODEL_VERSION（modelStore.ts・package.py）と、話者条件が変わるなら SPEAKER_MODEL（voiceStore.ts）も見直します。
