# PR 検証の運用

## 検証対象と制限

`.github/workflows/ci.yml` は GitHub-hosted Ubuntu で PR の仮マージコミットを検証する。チェックアウトを PR の head に変更しない。検証した SHA は実行サマリーに記録する。追加コミット後は前の検証を取り消し、新しいコミットを再検証する。

初期構成ではドキュメントだけの PR も全検証する。パスによる workflow のスキップは行わない。重い処理は一つの `validate` ジョブで直列実行する。別 PR の実行は別の GitHub-hosted VM を使うため、開発ホストの共有メモリを消費しない。

`pr-gate` は `always()` と `needs: [validate]` により、上流の失敗・スキップ時にも判定する。`validate` の結果が `success` の場合だけ通す。実行全体が中断されてゲートが動かなかった場合も、成功は記録されない。タイムアウトやロック取得失敗を成功に変換しない。

ローカルは `develop` 限定・共有ロック・Rust 1ジョブを維持する。CI 用環境変数をローカルで設定しない。self-hosted runner への置換は例外の対象外。

Linux 上の全 feature のコンパイル・テストが対象。Windows 固有コード、実機 GUI、実サービスとの接続、本番 release 最適化は別途検証する。テストで必要な外部サービスはテスト用に分離し、本番の認証情報を渡さない。

## 導入順序

1. この変更を develop 向け PR として作成し、実際の Actions で動作を確認する。
2. 既存コード由来も含め失敗原因を解消する。既存問題を別 Issue に記録しても、未解決のままゲートを緩めない。
3. 下記の試運転を行い、成功する最新の PR で `pr-gate` が記録された後、develop の保護設定を有効にする。
4. 最新差分のレビュー後に PR をマージする。自動マージの連携とデプロイ自動化は別の変更で扱う。

## develop の保護設定

- 必須 status check: `pr-gate`。発行元を GitHub Actions に限定する。
- `Require branches to be up to date before merging` を有効にする。develop が進んだら PR に取り込んで再検証する。
- PR 経由の取り込みを必須とし、直接 push・force push・ブランチ削除を防ぐ。
- 管理者にも適用し、検証結果を回避するマージを禁止する。
- 未解決のレビュー会話を残したままマージしない。

CL のレビューは別の条件として必要。同じ GitHub アカウントで CO と CL を動かす場合、自己承認を required review の代わりにはできないため、レビューの機械的な強制方法は連携設計時に決める。この検証経路の導入だけで CL の承認や自動マージを有効化しない。

保護設定は GitHub 上の設定であり、workflow を配置しただけでは有効にならない。導入 PR に実際の設定状況を記録する。

## 試運転

ローカルで `bash scripts/test-pr-validation.sh` を実行する。コンパイラは起動せず、隔離した一時 Git リポジトリとテスト専用ロックで以下を検証する。

- develop のローカル実行は許可し、作業ブランチと detached HEAD は拒否。
- hosted CI は許可したイベント・ref・SHA の組み合わせだけ許可。self-hosted、PR head、SHA 不一致は拒否。
- ロック競合で終了コード2、子プロセス失敗の終了コード維持、Rust 並列数の固定と上書き拒否。
- workflow に書かれた実際のゲートを実行し、success 以外の failure / cancelled / skipped / 空値・未知値を拒否。

GitHub でも試験 PR で確認する。

1. 正常時に `validate` と `pr-gate` が成功し、検証 SHA が PR の仮マージコミットと一致する。
2. 一時的な失敗を入れると `pr-gate` が失敗する。
3. 上流ジョブを一時的にスキップするとゲートは失敗する。
4. 追加コミットで再検証され、古い結果でマージできない。
5. develop 更新後、最新ベースで再検証するまでマージできない。

試験用の変更を残さず、最終コミットで全検証を再実行する。CI 制御ファイル自体の改変を防ぐ CODEOWNERS や必須 workflow は、CL 用アカウント・GitHub App の権限設計と合わせて別途検討する。
